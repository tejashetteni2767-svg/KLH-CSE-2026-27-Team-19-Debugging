FUNDAMENTALS OF OPERATING SYSTEMS

Linux Signals: Asynchronous Kernel IPC

What is a Signal?

A signal is a standardized software interrupt delivered by the Linux kernel to notify a user-space process that a specific event has occurred.

1. Event Triggered (Timer, User Ctrl+C, Syscall kill(2))
⬇
2. Kernel marks signal bit in Process Task Struct (task_struct->pending)
⬇
3. Scheduler switches context: Kernel -> User space transition
⬇
4. Process executes default action or custom sigaction() handler

Default Signal Dispositions

  • Term: Abruptly terminates the process.
  • Core: Terminates the process and generates a memory core dump for debugging.
  • Stop: Suspends execution; process transitions to TASK_STOPPED.
  • Cont: Resumes execution if previously suspended.
  • Ign: Completely ignored by the kernel and discarded.

DEEP DIVE COMPARISONS

Critical Kernel Distinctions Faculty Ask About

1. SIGSTOP vs. SIGTSTP (Pause Mechanisms)

SIGSTOP (19)

Sent by our controller. Handled directly by the kernel scheduler. The process never receives the signal in user space. Cannot be intercepted, blocked, or ignored under any condition.

SIGTSTP (20)

Sent by the terminal driver when user presses Ctrl+Z. Can be intercepted or ignored by user code (e.g. Vim, text editors) to clean up terminal states before stopping.

2. SIGTERM vs. SIGKILL (Termination Mechanisms)

SIGTERM (15)

Cooperative request. The target process intercepts it, executes cleanup handlers (flushes disk buffers, closes sockets, finishes transactions), and exits cleanly.

SIGKILL (9)

Uncatchable eviction. The kernel immediately removes the process from the runqueue, tears down address space, and reclaims memory. No user cleanup code ever executes.

KERNEL INTERNALS

Process States in the Linux Scheduler

The 5 Canonical Task States:

  • R TASK_RUNNING: Process is either actively running on CPU or waiting in the scheduler's runqueue.
  • S TASK_INTERRUPTIBLE: Process is sleeping, awaiting an event or I/O. Can be awakened by signals.
  • D TASK_UNINTERRUPTIBLE: Waiting on hardware I/O; ignores signals until I/O finishes.
  • T TASK_STOPPED: Execution suspended by SIGSTOP or SIGTSTP. Only SIGCONT or SIGKILL can alter this state.
  • Z EXIT_ZOMBIE: Process has finished executing, but its parent has not yet read its exit code via waitpid().

ProcFS Introspection & Hex Mask Decoding

Reading /proc/[pid]/status

The Linux kernel exposes process metadata directly through the virtual procfs filesystem. Our utility parses:

  • State: Extracts character code (R, S, T, Z).
  • VmRSS: Actual physical resident memory in RAM.
  • Threads: Number of kernel schedulable threads.

Hexadecimal Signal Bitmasks

The kernel represents registered signal behaviors as 64-bit hexadecimal masks:

SigCgt: 0000000000004a03

Our Decoding Algorithm

To identify which signals are caught, our C code applies a bitwise right-shift for each signal number 1 <= signo <= 31:

for (int signo = 1; signo <= 31; signo++) {
    if ((mask >> (signo - 1)) & 1ULL) {
        // Signal 'signo' is registered!
        printf("%s ", get_sig_name(signo));
    }
}

OS RESOURCE MANAGEMENT

Zombie Processes: Root Cause & Prevention

What causes a Zombie Process (State: Z)?

When a child process terminates, its memory space and file descriptors are freed, but its entry in the Kernel Process Table (PID, exit code, CPU stats) remains until the parent calls wait() or waitpid().

⚠️ The Danger: If a parent spawns many children without reaping them, the system runs out of PIDs (kernel PID exhaustion), preventing new processes from starting!

Our Dual Solution Architecture

  1. Asynchronous SIGCHLD Handler: The controller installs a signal handler for SIGCHLD that reaps children with waitpid(-1, &status, WNOHANG) without blocking the parent!
  2. Orphan Reparenting to Init (PID 1): If a parent crashes, the Linux kernel automatically reparents orphan processes to systemd/init, which routinely reaps zombies.

VIVA VOCE PREPARATION

Top 5 Tough Questions Faculty Ask & Answers

Q1: Can a process intercept or block SIGKILL or SIGSTOP? Why or why not?
Answer: Absolutely not. In the Linux kernel, SIGKILL and SIGSTOP bypass user-space signal tables and are handled directly in the kernel scheduler. This ensures the system administrator / root can always terminate runaway or malicious processes. Attempting sigaction(SIGKILL, ...) returns -1 with errno EINVAL.
Q2: What is the difference between SIGHUP reload and process restart?
Answer: SIGHUP allows in-place reload: the process keeps its original PID, open file descriptors, and socket bindings while re-reading configuration files. A respawn restart completely kills the existing process and forks a new one, changing the PID and re-initializing from scratch.
Q3: What happens to child processes when a parent process receives SIGKILL?
Answer: Child processes become orphans. The Linux kernel reparents them to PID 1 (systemd or init), which adopts them and periodically calls wait() to reap them when they finish.
Q4: Why use waitpid with WNOHANG in SIGCHLD rather than blocking wait?
Answer: If multiple child processes terminate simultaneously, standard signals are not queued—they are merged into a single pending bit. A non-blocking while(waitpid(-1, &status, WNOHANG) > 0) loop reaps all finished children without freezing the parent process.
Q5: How does the kernel know which signals a process has caught?
Answer: Inside task_struct, the kernel maintains signal structure pointers with bitmasks for sig_catch, sig_ignore, and blocked. These are exported to user space via /proc/[pid]/status as SigCgt, SigIgn, and SigBlk in 64-bit hexadecimal.

4. Comprehensive Viva Voce Questions & Answers

Question 1: Explain the difference between synchronous exceptions and asynchronous signals.

Synchronous exceptions (e.g., SIGSEGV on invalid memory access, SIGFPE on divide by zero) are triggered directly by the executing instruction stream and delivered immediately. Asynchronous signals (e.g., SIGSTOP, SIGTERM, SIGKILL) are generated by external entities (another process or hardware clock) and delivered when the target process is scheduled.

Question 2: Why are global variables inside signal handlers marked volatile sig_atomic_t?

The volatile keyword prevents the compiler from optimizing variable reads into CPU registers, ensuring memory is read fresh on every access. The type sig_atomic_t guarantees that read and write operations are atomic and cannot be interrupted midway by another signal handler.

Question 3: How does the kernel deliver signals to a process that is currently in TASK_STOPPED?

When stopped by SIGSTOP, all pending signals except SIGKILL and SIGCONT remain in the pending queue and are not delivered until the process transitions back to TASK_RUNNING via SIGCONT. SIGKILL acts immediately regardless of stopped state.
